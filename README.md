# 러브 아일랜드 — cgoing 의 섬

메뉴 없는 3D 개인 사이트. 캐릭터로 섬을 걸어다니며 컨텐츠를 발견하고,
같은 순간에 들어온 사람과 채팅하고 밀치며 논다.

---

## 시작하기

```bash
pnpm install
pnpm db:up          # Docker 로 Postgres 17 기동 (love-island-pg)
pnpm db:migrate     # 스키마 적용
pnpm dev            # http://localhost:3000
```

`.env.local` 이 필요하다:

```
DATABASE_URL=postgres://island:island@localhost:5432/love_island
IP_HASH_SALT=아무_긴_문자열
```

배포(Vercel)에서는 `DATABASE_URL` 을 Neon/Vercel Postgres 로, `IP_HASH_SALT` 를
직접 만든 값으로 넣는다. 로컬 기본값을 그대로 쓰면 IP 해시가 예측 가능해진다.

## 구조

```
app/            라우트. 최대한 얇게. _scene/ 이 game 과 features 를 합성하는 유일한 자리
game/           3D 런타임
  core/           좌표계 · 고정 타임스텝 · A* · 섬 지형 · 상호작용 레지스트리 (three 없는 순수 로직 포함)
  player/         이동 시뮬레이션 · 경로 추종 · 캐릭터
  world/          바다 · 바다바닥 · 지형 · 하늘 · 태양 · 야자수 · 감정표현 파티클 · 셰이더
  net/            접속자 위치 교환 · 보간 버퍼
  camera/ hud/ dev/
features/       수직 슬라이스. 각자 3D + UI + API 를 소유하고, index.ts 로만 밖에 노출된다
  guestbook/      게시판(포스트잇) · 바닥 쪽지 · 코르크판 무한스크롤
  career/         책상·노트북 · 포트폴리오 사이트를 iframe 으로 띄운다
  album/          액자 벽 · 사진첩       ← content.ts
server/         DB · 검증 · 레이트 리밋. 클라이언트 번들에 절대 안 들어간다
shared/         타입 · 상수 · 통신 계약. 아무것도 import 하지 않는 잎(leaf)
docs/adr/       왜 그렇게 했는지에 대한 기록
```

의존 방향은 한 방향뿐이다:

```
shared ← game/core ← game/* ← features ← app
shared ← server ← app
```

**이건 문서가 아니라 실행되는 제약이다.** `biome.json` 의 override 가 레이어별로
금지된 import 를 에러로 막는다. 확인하려면 일부러 어겨보면 된다:

```bash
echo 'import { Vector3 } from "three"; export const x = Vector3;' > shared/probe.ts
pnpm lint   # → shared/ 는 브라우저·워커·노드 어디서든 돌아가야 합니다
rm shared/probe.ts
```

## 단위 규약

`shared/constants.ts` 최상단에 박아뒀다.

- 길이: 1 three 유닛 = 1 미터
- 축: +Y 위, **-Z 북쪽**, +X 동쪽. 캐릭터의 로컬 전방은 -Z
- 회전: 라디안, Y축 yaw 하나만
- 시간: 초(부동소수). 네트워크 타임스탬프만 밀리초 정수
- 해수면 y = 0

**입체는 전부 `game/world/curvature` 의 `CurvedMaterial`(빛 받음) 또는
`CurvedBasicMaterial`(빛 안 받음) 을 써야 한다.** 지형만 곡률을 타고 캐릭터는
안 타면 멀어질수록 캐릭터가 땅에서 떠오른다 — 기본 카메라 거리에서 0.75m,
캐릭터 반 키만큼이다.

이 버그는 **세 번** 났고 세 번 다 "오브젝트가 공중에 떠 있다"로 보고됐다.
코드만 봐서는 안 보이는 종류라(`<meshStandardMaterial color="red" />` 는 어느 모로 보나
정상이다) 이제 `game/world/materialCoverage.test.ts` 가 소스를 훑어서 막는다.
곡률 셰이더의 함정 네 가지는
[docs/adr/0007](docs/adr/0007-local-space-curvature-pitfalls.md) 에 정리해뒀다.

섬의 모양은 `game/core/island.ts` 의 하모닉 세 개가 정한다. 이 계수는
지형 메시 · 네비 그리드 · 바다 물거품 세 곳이 함께 본다 —
`game/world/shaders.ts` 에 GLSL 로 손수 이식돼 있으니 한쪽만 고치면 물거품이 어긋난다.

## 성능 예산

`shared/constants.ts` 의 `PERF_BUDGET`. 개발 중 좌상단 계기판이 초과 항목에 `!` 를 붙인다.

측정치(1440x860, Chrome): **60fps · 드로우콜 ~60 · 삼각형 165k · 지오메트리 42 · 텍스처 6**

큰 오브젝트는 조각을 **정점 색으로 구워 한 덩어리**로 합친다(`game/world/meshKit.ts`).
게시판에 포스트잇 12장을 메시로 붙였더니 그것만 드로우콜 36개였다 —
화면에 보이는 건 판 하나인데. 지금은 게시판 1 · 야자수 그루당 1 · 책상 3 이다.

감정표현 파티클도 입자가 몇 개든 **드로우콜 1**이다 — 링버퍼 하나에 초기 조건만
써넣고 궤적은 셰이더가 푼다. 비용이 입자 수가 아니라 버스트 횟수에 비례한다.

## 실시간

같은 순간에 섬에 있는 사람들이 서로 보인다. WebSocket 도 Durable Objects 도 쓰지 않는다 —
**Postgres 의 presence 테이블 + HTTP 왕복 한 번**으로 "내 위치 올리기"와 "남들 위치 받기"를
같이 한다. Vercel 위에서 그대로 돌아가고 새 인프라가 필요 없다.

- 움직일 때만 200ms 주기, 서 있으면 3초 주기 (dead reckoning)
- 백그라운드 탭은 아예 안 보낸다
- 탭을 그냥 닫아도 12초 뒤 TTL 이 정리한다
- 200ms 주기의 뚝뚝 끊기는 좌표는 `game/net/interpolation.ts` 가 메운다 —
  **320ms 과거를 렌더**해서 항상 두 스냅샷 사이에 있게 만든다

동시 접속이 상시 두 자릿수가 되면 이 방식은 더 이상 싸지 않다. 판단 근거와
갈아탈 시점은 [docs/adr/0004](docs/adr/0004-presence-over-postgres-instead-of-durable-objects.md) 에.

## 내 내용으로 바꾸기

글은 DB 가 아니라 코드에 있다. 자주 안 바뀌는 원고라 이게 더 단순하다.

| 무엇 | 어디 |
|---|---|
| 이름 · 연락처 · 포트폴리오 주소 · 사진첩 | **`content/profile.json`** |
| 사진 파일 | `public/photos/` (JSON 의 `src` 에 `/photos/파일명.jpg`) |
| 프로필 사진(깃발) | `public/cgoing-profile.png` |
| UI 문구 · 봇 대사 · 전리품 이름 | `shared/strings.ts` |

코드를 안 열고 **JSON 하나만 고쳐 커밋하면** 내용이 바뀐다. 자세한 건 [content/README.md](content/README.md).

잘못 적으면 `shared/content.ts` 의 zod 스키마가 **어느 필드가 틀렸는지 짚어서** 막는다.
사진 경로만 적고 파일을 안 넣은 것도 테스트가 잡는다 — 원고는 조용히 틀리는 게 가장 나쁘다.

**경력은 이 JSON 에 없다.** `owner.site` 가 가리키는 포트폴리오를 책상 노트북이
그대로 띄운다(아래 "노트북은 원본을 띄운다").

사진첩은 아직 뼈대다(`tint` 카드 여섯 장). `public/photos/` 에 넣고 `src` 를 적으면 바뀐다.

## 한국어와 영어

`/` 는 한국어, `/en` 은 영어다. `?lang=en` 도 같은 결과다 — 링크로 공유하기엔 경로가,
그 자리에서 바꿔보기엔 쿼리가 낫다. 좌상단 간판의 `KO / EN` 로도 갈아탄다.

문구는 전부 `shared/strings.ts` 한 파일에 있다. 컴포넌트 옆에 흩어두면 "영어에 뭐가
빠졌나"를 세는 방법이 없어지는데, 한곳에 모아 `const en: Dict` 로 못박으면
**빠진 번역이 타입 에러**가 된다. 인자가 들어가는 문구는 문자열이 아니라 함수다 —
`"{n}명"` 같은 자리표시자는 어순이 다른 언어에서 깨진다.

원고(`content/profile.json`)는 항목마다 `"한 줄"` 또는 `{ "ko": "…", "en": "…" }`
둘 다 받는다. 하나만 적으면 그 값이 모든 언어에 쓰인다 — **번역을 강요하지 않는 게
요점이다.** 원고는 주인장의 것이라 없는 영어를 코드가 지어낼 수 없고, 안 적었다고
화면이 비어서도 안 된다.

⚠ 지금 언어는 **모듈 전역**이다(`setLocale`). 서버에서는 요청끼리 공유되므로 원래
위험한 패턴인데, 이 앱에서 안전한 이유는 하나뿐이다 — **섬 전체가 `ssr: false` 라
서버에서는 `t()` 를 부르는 코드가 아예 안 돈다.** 서버 컴포넌트에서 `t()` 를 부르는
순간 이 전제가 깨진다. 로딩 화면이 영어로 고정된 것도 그래서다.

⚠ 문구를 **모듈 상수에 담지 않는다.** `const LINES = [t().banner.tagline]` 처럼 쓰면
import 시점에 값이 굳는데, 그때는 아직 언어가 안 정해져 있어서 영어로 들어와도 한글이
그려진다. 실제로 배너에서 한 번 겪었다 — 상수 대신 함수로 두면 된다.

봇 대사는 **언어가 달라도 같은 키**가 오간다. 그래서 한국어로 보는 사람과 영어로 보는
사람이 같은 봇을 보면서 각자 자기 언어로 듣는다 — 대사 대신 키를 보내는 설계의 덤이다.

## 안내 봇 cgoing-bot — 하나를 여럿이 함께 본다

섬에 봇이 하나 있고, **누가 말을 걸든 모두가 같은 봇이 움직이는 걸 본다.**
그게 되려면 두 가지가 필요했다:

1. **결정하는 사람이 하나** — playerId 가 가장 작은 사람이 소유자다.
   목록만 보면 각자 같은 답이 나오므로 협상 절차가 없고, 소유자가 나가면
   다음 사람이 자동으로 이어받는다. (`game/core/bot/state.ts`)
2. **위치가 아니라 결정을 나눈다** — "언제 어디서 어디로" 만 보내고 위치는 각자
   계산한다. 경로는 같은 A* 를 같은 격자에 돌려 얻고, "지금" 은 이미 있는
   서버 보정 벽시계다. 그래서 **결정 하나(100자 남짓)로 전원이 같은 봇을 본다.**

대사도 안 보낸다 — 모두 같은 번들을 받았으니 **대본 키만** 보낸다.
처음엔 대사를 통째로 실었다가 계약 상한(80자)에 걸려 400 이 났는데,
상한을 올리는 건 이미 가진 걸 다시 보내는 낭비를 감추는 것이었다.

봇은 사람 모양이 아니다 — 다리 없이 떠 있는 로봇이다. 사람 모양이면 접속자 중 하나로
보이고, 그러면 말을 걸어볼 마음이 안 생긴다.

머리 위에는 **3D 마우스 커서**가 떠서 콕콕 찌른다. 이름표는 눌러야 뭔가 나오는
버튼인데 화면에 그냥 놓여 있으면 그게 버튼인 줄 모른다 — 커서는 설명 없이도 통하는
도상이라 "여기를 누르세요" 라고 글로 쓸 필요가 없다. 한 번 눌러본 뒤에는 사라진다.

⚠ 누르는 자리는 이름표가 아니라 **봇 자체**다. 이름표만 눌리게 뒀더니 24m 밖에서
60px 짜리 알약을 정확히 맞춰야 했고 모바일에서는 사실상 불가능했다. 봇을 감싸는
투명한 구를 두면 "봇을 누른다" 가 곧 조작이 된다. `visible={false}` 는 광선에 안 잡히므로
**투명도 0 · 깊이 미기록**으로 둔다 — 렌더는 되지만 화면에 흔적은 없다.
카메라 방위가 고정이라 XY 평면에 누운 도형은 늘 정면을 향한다 — 빌보드 계산이 필요 없고,
몸이 도는 만큼(`rotation.y`) 반대로 돌려주는 한 줄이면 끝이다.

peer 쪽에서는 결정이 도착하기까지 걸린 시간만큼 권위 위치가 앞서 있다. 그대로 그리면
1~2m 씩 건너뛰므로, **그리는 위치를 따로 두고** 지수 감쇠로 따라가게 한다.

⚠ `findPath` 는 **출발점을 빼고** 돌려준다(플레이어는 이미 거기 서 있으니까).
그걸 그대로 봇 경로로 쓰면 직선 구간에서 경로가 한 점이 되고, 봇이 곧장 찍힌다 —
그게 "순간이동" 의 정체였다.

### 봇 기능 늘리기

`game/core/bot/script.ts` 의 `BOT_TOPICS` 에 id 와 데려갈 자리를 한 줄 더하고,
`shared/strings.ts` 의 `bot.topics` 에 같은 id 로 말을 적으면 끝이다.

```ts
// script.ts
{ id: "secret", guideTo: [12, -8] }
// strings.ts — ko 와 en 양쪽에
secret: { label: "비밀 있어?", lines: ["…없는데요."] }
```

## 잠금은 없다

한때 도장 세 개를 모아야 경력·사진첩·방명록이 열렸다. "들어오면 3분이면 볼 게 없다"
를 풀려던 장치였는데, 이건 포트폴리오다 — 작품을 보러 온 사람 앞에 미니게임을
세워두는 순간 앱이 목적을 배신한다. 걷어냈다.

섬을 돌게 만드는 건 잠금이 아니라 **볼 것이 흩어져 있다는 사실**이어야 한다.

## 섬은 하트다

러브 아일랜드니까. 해안선은 고전 하트 곡선을 극좌표로 바꿔 **사인 급수 9항으로 근사**한
것이다(`shoreRadiusAt`). 좌표표를 쓰면 GLSL 쪽에 넘길 방법이 마땅치 않은데 —
물거품이 같은 해안선을 알아야 한다 — 급수면 TS 와 GLSL 이 같은 식 한 줄을 공유한다.

좌우 대칭이라 코사인 항은 전부 0 이 됐고 홀수 사인 항만 남는다. 접히는 축은
꼭지(+Z)와 골(-Z)을 잇는 세로축이라 `r(θ) = r(180°−θ)` 다. 미니맵을 보면 하트가 보인다.

⚠ 육지 최저 높이는 **파도보다 높아야** 한다. 전에는 `max(0, ...)` 로 잘라서 언덕 잡음이
깊게 파인 자리가 정확히 해수면이 됐고, 파도가 ±0.3m 흔들리는 순간 그 위를 물이 덮었다 —
**육지 한복판에 물웅덩이가 생겼다.** 지금은 물가에서만 0 까지 내려간다.

## 바다 한가운데 깃발

섬 정북 58m 물 위에 큰 배너가 서 있다. 섬 밖은 걸어서 못 가는 영역이라 그냥 빈 물이었는데,
거기 깃발을 세우면 못 가는 곳이 "볼 것"으로 바뀐다 — 경계가 벽이 아니라 배경이 된다.

천에는 `public/cgoing-profile.png` 를 **원으로 오려** 왼쪽에 붙이고 오른쪽에 이름을 적는다.
이미 원형으로 그려진 정사각 이미지라 원으로 클립하면 배경 모서리가 깨끗이 지워진다.
사진은 비동기로 도착하므로 같은 그리기 함수를 **두 번** 부른다 — 처음엔 사진 없이,
로드가 끝나면 사진과 함께(`texture.needsUpdate = true`). 레이아웃이 사진 유무와 무관해서
글자가 안 튀고, 파일이 없어도 빈 원판만 남을 뿐 화면이 깨지지 않는다.

⚠ 캔버스 텍스처에는 `colorSpace = SRGBColorSpace` 를 준다. 안 주면 three 가 sRGB 값을
선형으로 읽어 전체가 허옇게 뜬다 — 글자만 있을 땐 넘어갔지만 사진이 들어오면 바로 티가 난다.

테두리는 없다. 천을 두른 사각테와 사진을 감싼 링이 있었는데 둘 다 안쪽 여백을 먹으면서
내용을 가장자리로 밀어붙였다. 천은 이미 나무 기둥 둘이 잡고 있어서 선을 그어줄 필요가 없다.
대신 사진+글 덩어리의 폭을 **재서** 가운데 놓는다 — x 좌표를 손으로 박아뒀을 땐 이름이
조금만 길어져도 한쪽으로 쏠렸고, 여백을 늘리려면 세 군데를 같이 고쳐야 했다.

높이는 세 가지에 끼여 있다. 깃대를 낮추면 방명록 게시판과 화면에서 포개지고, 올리면
북쪽 물가에서 천 윗단이 화면 밖으로 나간다(다가갈수록 곡률 낙차가 거리보다 빨리 줄어서
멀리 있는 것이 화면에서 **올라온다**). 그래서 깃대는 17m 로 두고 **천을 짧게**(5m) 했다 —
위 끝은 깃대에 매여 그대로고 아래 끝만 올라오므로, 게시판 이름표가 앉을 자리가 비워진다.

## 밤 연출

밤이 너무 어두워서 "밤"이 아니라 "고장"으로 보였다. 달빛이 유난히 밝은 밤으로 올렸다.

별똥별과 불꽃놀이는 `game/world/nightShow.ts` 가 **시각만으로** 정한다.
불꽃은 달이 밤의 25% · 50% · 80% 지점을 지날 때 3~6발씩 올라간다.
누가 "지금 쏴" 라고 알리는 방식이면 그 사람이 나가는 순간 연출이 멈춘다.
시각에서 유도하면 아무도 책임지지 않아도 모두가 같은 순간에 같은 걸 보고, 통신이 0 이다.
낮밤 순환·봇과 정확히 같은 원리다.

### 터지는 자리는 깃발보다 뒤다

섬 중심 기준 **64~78m**, 정북 **±12°~42°**. 세 가지가 이 숫자를 정한다.

**뒤**여야 한다. 예전엔 해안선 바로 바깥(25~32m)에서 터뜨렸는데, 정북 58m 에 서 있는
배너보다 카메라에 가까워서 폭죽이 **깃발 앞에서** 터지는 그림이 됐다. 하늘의 불꽃이
깃발을 가리면 그건 하늘이 아니라 깃발과 카메라 사이에 낀 무언가다 — 원근이 어긋나 보인다.

**가운데는 비운다**(±12° 안쪽). 뒤에서 터지니 가려도 이상하진 않지만, 매번 깃발 뒤에서만
터지면 연출이 반쯤 낭비된다. 양옆으로 비켜 쏘면 깃발을 가운데 두고 좌우에서 피어오른다.
바깥 한계 42° 는 카메라 가로 화각(±33°)이 정한다 — 그 밖은 아무도 못 본다.

⚠ **멀리 보내면 높이도 같이 올려야 한다.** 곡률이 거리 제곱으로 끌어내리기 때문이다
(110m 에서 16m). 한때 46~70m 로 보냈다가 하나도 안 보였던 게 그 높이를 안 올려서였다 —
거리 자체가 문제가 아니었다. 지금은 `shellSpeedFor(power)` 가 규모와 함께 올린다.
규모와 거리가 같이 가는 구조라 배수 하나로 맞는다.

⚠ 그렇다고 규모를 **발사 속도로** 내면 안 된다. 예전에 그렇게 했다가 터지는 지점이
화면 위로 벗어났다 — 태양을 올렸다가 화면 밖으로 보냈던 것과 같은 함정이다.

### 화면에서 하늘은 11° 뿐이다

카메라가 23° 숙이고 세로 화각이 40° 라 프레임 맨 윗줄이 이미 **수평 아래 3°** 다.
그 아래로 곡률에 접힌 먼바다가 13.9° 지점부터 올라오므로, 하늘로 보이는 띠는
**수평 아래 3°~14°** 뿐이다. 70m 거리로 환산하면 지면 기준 0.5m ~ 15m.
불꽃 설계가 전부 이 숫자에서 나온다:

- 터지는 높이는 규모와 무관하게 7~9m — 띠의 한가운데
- 퍼지는 반지름 상한 7.5m — 지름 15m 가 띠를 꽉 채우는 크기
- 규모는 반지름 · 개수 · 연쇄로 낸다

밤 불꽃이 "나약했던" 진짜 이유는 세 가지였고 셋 다 이 계산으로 잡혔다.
**첫째**, 터지는 높이는 `SHELL_SPEED * power` 로 구하면서 올라가는 꼬리는 `SHELL_SPEED`
로 그렸다. 큰 발은 꼬리가 10m 에서 끊기고 폭발은 25m — 프레임 밖 — 에서 일어났다.
`reactionBursts.test.ts` 의 "올라가는 꼬리가 터지는 높이까지 닿는다" 가 지킨다.
**둘째**, 별 속도를 4.5~10 으로 넓게 뿌려서 구 안쪽이 채워졌다. 실제 폭죽이 동그란 건
별이 전부 **같은 속도**로 날아가 얇은 껍데기에 놓이기 때문이다 — 속도 폭을 10% 로 좁힌
것 하나가 "얼룩"과 "원"을 갈랐다. **셋째**, 저항 계수가 크기뿐 아니라 **언제 그 크기가
되는지**도 정한다는 걸 놓쳤다. 시간상수 1/k 가 0.74초라 원이 다 퍼질 때쯤 별은 이미
흐려져 있었다 — 가장 밝은 순간의 원이 최종 크기의 절반도 안 됐다.

### 연쇄는 재귀다 — 3단까지 간다

한 발이 터지면 그 원 위의 별 대여섯 개가 **다시** 터지고, 그것들이 또 두세 개씩 터진다.
2차만 있으면 "한 번 더 터졌다" 로 끝나는데, 3차가 있어야 하늘이 계속 번져 나간다.

손으로 펼쳐 쓰면 같은 코드가 세 벌 생기고 비율을 바꿀 때마다 세 곳을 고쳐야 한다.
층마다 다른 건 **개수 · 크기 · 시점** 세 숫자뿐이라(`BREAK_LAYERS`), 배열로 두고
자기를 부르면 층은 곧 배열 길이가 된다.

파티클과 같은 수법으로 공짜다. 별의 궤적은 해석해라 **미래 위치를 지금** 계산할 수 있어서,
2·3차 폭발도 초기 조건 한 번 써넣는 것으로 끝난다 — 터지는 순간 CPU 는 아무 일도 안 한다.
큰 발 하나가 7천 입자쯤 되지만 죽은 입자는 정점 셰이더 첫 줄에서 접히고, 살아 있는 것도
3~7px 짜리 점이라 비용이 거의 안 붙는다.

### 퍼지는 속도와 밝은 시간은 다른 손잡이다

여기서 세 번 헛디뎠다. 저항 1.35 로는 원이 다 퍼지는 데 2초가 걸려서 그때쯤 별이
이미 흐려졌다 — "작은 폭죽". 그래서 2.4 로 올렸더니 이번엔 **너무 빨리 터져서**
순식간에 지나갔다. 답은 저항이 아니라 **수명**이었다. 지금은 1.15 로 느긋하게 퍼지게 두고
수명을 시간상수(0.87초)의 네 배 이상으로 늘렸다.
`reactionBursts.test.ts` 가 `life > 4/drag` 를 지킨다 — 저항을 만질 때마다 수명이
따라오게 강제하는 게 이 한 줄의 목적이다.

같은 이유로 입자는 **작고 많다**(0.1~0.18m · 큰 발에 9천 개 이상). 큰 점 몇 개는
물감이고 작은 점 수천 개라야 불꽃이다. 셰이더의 수축률도 0.35 → 0.62 로 완화했다 —
3px 짜리 점이 1px 이 되면 그건 그냥 없는 것이다.

⚠ 밤 연출에 축포를 섞지 않는다. 축포는 1.3m 에서 뿜어 3m 남짓 오르는데, 70m 밖 바다
위에서 그러면 하늘이 아니라 **수평선의 색색 얼룩**으로 보인다. 가까이서 좋은 연출이
멀리서도 좋으리라는 보장이 없다.

### 섬광은 뺐다

한때 터진 자리에 반지름 1.5배짜리 흰 불덩이를 얹고, 실제 `pointLight` 두 개로 섬 전체를
번쩍이게 했다. 잔디 밝기를 재서 세기를 맞출 만큼 공들였고 밤바다 사진처럼 그럴싸했다.

그런데 화면에서는 **색이 날아가 하얀 얼룩**이 됐고, 그 얼룩이 정작 봐야 할 원의 모양을
덮었다. 밝기로 웅장함을 내려던 시도였는데, 웅장함은 밝기가 아니라 퍼지는 크기와
겹치는 발 수에서 나온다. 지어낸 빛보다 별 만 개가 낫다.

빼고 나니 광원 둘이 사라져서 **모든 머티리얼의 조명 계산**이 같이 가벼워졌다.
`reactionBursts.test.ts` 의 "눈부신 흰 덩어리를 남기지 않는다" 가 입자 크기 상한으로
이 결정을 지킨다 — 다음에 누가 크기를 만지다 실수로 되돌리는 걸 막는다.

## 낚시 — 진짜 커피가 걸린다

건질 수 있는 건 **두 가지뿐**이다: 꽝, 그리고 진짜 아메리카노 쿠폰.

꽝 카드에는 확률을 한 줄 적는다("1.4% 확률로 아메리카노 쿠폰이 나옵니다"). 그 숫자는
**전리품표에서 계산한다**(`REAL_CHANCE_PERCENT`) — 손으로 적어두면 무게를 만지는 순간
화면이 거짓말을 시작하는데, 그 거짓말은 아무도 못 알아챈다. 확률은 눈으로 검산할 수
있는 종류의 값이 아니다.

처음엔 등급을 다섯 개 두고 물고기며 배경화면이며 늘어놨다. 그런데 그것들은 받아도
아무 일도 안 일어나는 물건이라, 결국 **"꽝인데 이름만 다른 것"** 이었다.
이름을 늘리는 건 재미가 아니라 소음이다. 걸린 게 하나뿐이라야 그 하나가 무엇인지
분명해지고, 얼마가 나갈지 계산도 된다. 꽝일 때 카드에 "꽝" 이라고 크게 쓰고
바로 아래 그 위에 뭐가 있는지 적는 것도 같은 이유다 — 뭘 노리는지 모르면
한 번 던져보고 끝이다.

⚠ **주사위는 서버가 굴린다.** 클라이언트가 "쿠폰 뽑았다"고 주장할 수 있으면
진짜 보상을 걸 수 없다. `/api/catch` 가 굴리고 결과를 `catch` 테이블에 남기므로,
보내온 코드가 진짜인지 확인할 수 있다:

```sql
SELECT * FROM catch WHERE code = '보내온 코드';
-- claimed_at 이 비어 있으면 아직 안 쓴 것. 사주고 나면 채운다.
```

미니게임을 실제로 했는지는 서버가 알 수 없어서 **시간당 30회 제한**이 유일한 방벽이다.
그 선이면 자동화해서 커피 한 잔을 노릴 값어치가 없어진다.

낚시는 팝업이 아니라 **월드 안에서** 벌어진다. 캐릭터가 낚싯대를 들고 찌를 바다로
던지고, 찌가 파도에 까딱이다가 입질하면 쑥 잠긴다. 화면에 남는 UI 는 지금 뭘
눌러야 하는지 알려주는 한 줄뿐이다 — 모달이 뜨는 순간 3D 가 배경이 되고,
배경이 되면 그건 게임이 아니라 게임의 **설명서**가 된다.

낚시터는 하트의 **아래 꼭지**, 섬 남쪽 끝이다. 사진첩이 동쪽이고 방명록이 북쪽이니
남쪽이어야 셋이 섬을 고루 나눈다.

⚠ 남쪽이라고 **정남향 물가**에 두면 안 된다. 카메라는 방위가 고정이라 늘 남쪽 위에서
북쪽(-Z)을 보므로, 정남향 물가에서는 **카메라 쪽으로** 던지게 되어 찌가 화면 아래로
빠져나간다(실제로 그래서 한때 북쪽으로 옮겼었다). 하트의 아래 꼭지는 남쪽으로 길게 뻗은
모래톱이라 **옆면이 서쪽을 향한다** — 그 옆면에 서면 위치는 남쪽이면서 던지는 방향은 옆이다.
해안 법선 140° → 화면 중앙에서 가로 23° · 아래 33°, 화각은 가로 ±33° · 아래 3~43° 다.

## 하루가 3분이다 — 그리고 모두에게 같은 시각이다

`game/world/dayNight.ts` 가 위상 하나를 풀고, 하늘 · 태양 · 달 · 별 · 방향광 ·
바다색 · 안개가 그 결과를 **읽기만** 한다. 각자 시계를 읽으면 하늘은 밤인데
바다만 대낮인 화면이 나온다. 매 프레임 바뀌는 값이라 리액트 상태가 아니라
살아 있는 객체 하나를 공유한다(곡률 유니폼과 같은 방식).

위상의 기준은 **epoch 벽시계**다. 페이지를 연 뒤 경과 시간으로 굴리면 먼저 들어온
사람은 밤인데 방금 들어온 사람은 아침이 된다 — 같은 섬에 있다는 감각이 거기서 깨진다.
벽시계를 쓰면 **아무것도 주고받지 않고** 전원이 같은 시간대를 본다.
낮밤을 맞추자고 통신을 늘릴 이유가 없다.

시계가 틀어진 기기는 `game/net/serverClock.ts` 가 끌어온다. presence 응답의
`Date` 헤더가 곧 서버 시각이라 **새 요청을 하나도 안 늘린다.** 헤더는 1초 단위고
왕복 지연도 안 빼주지만, 180초 주기에서 1~2초는 1% 남짓이라 눈에 안 보인다.
그보다 작은 차이는 무시한다(deadband) — 잡음을 따라가면 하늘이 미세하게 떨린다.

⚠ 천체 궤도의 고도가 **음수**인 건 실수가 아니다. 카메라가 19° 숙이고 세로 화각이
40° 라 기하학적 지평선(0°)이 이미 화면 맨 윗줄이고, 화면에서 넓게 하늘로 보이는 띠는
곡률 셰이더가 먼바다를 아래로 접어 드러난 **지평선 아래** 각도대다.
현실적인 고도(9°, 55°)로 올렸던 해와 별이 전부 화면 밖에 있었던 이유가 이것이다.

그림자를 만드는 빛은 보이는 해와 **다른 궤도**를 돈다. 보이는 해(-15°~-2°)로
그림자를 만들면 지평선 아래에서 빛이 와 지형이 밑에서 조명된다.

## 캐릭터는 id 에서 나온다

`game/player/characterLook.ts` 가 playerId 를 해시해서 색 · 귀 모양 · 머리 크기 ·
몸 길이 · 액세서리를 뽑는다. 서버에 외형을 저장하지 않아도 **그 사람은 언제 봐도 그 모습**이고,
아무도 관리하지 않아도 알아서 일관된다.

한 명은 메시 **하나**다(`characterGeometry.ts`). 조각으로 두면 한 명에 드로우콜 열이라
다섯 명만 모여도 예산을 넘겼다. 같은 모습은 지오메트리를 재사용하므로
사람이 늘어도 GPU 버퍼는 모습의 가짓수만큼만 늘어난다.

팔만 따로 돈다. 몸 옆으로 들었다 내리는 **사이드 래터럴 레이즈** 동작이다 —
X 축으로 앞뒤로 흔들었더니 그건 걷는 동작이라 가만히 서 있는 캐릭터가 제자리걸음하는
것처럼 보였다. 좌우가 **같은 위상**인 것도 그래서다. 한쪽씩 올리면 그건 운동이 아니라 인사다.
속도는 사람마다 다르다(3~9 rad/s = 0.7~2.1초에 한 번). 다 같으면 인형 여럿이 같은
태엽으로 돌고, 너무 느리면 움직이는 건지 멈춘 건지 알 수가 없다.

⚠ 팔 캡슐은 **어깨보다 위로 조금 더 올라온다.** 팔이 내려가 있을 땐 몸통에 파묻혀서
이게 없어도 붙어 보이는데, 옆으로 들어 올리면 어깨를 축으로 회전하면서 캡슐 위 끝이
축 바깥으로 돌아 나가 몸통과 팔 사이에 4~5cm 틈이 생겼다 — **팔이 떨어져 보였다.**
회전축에서 거리 d 안쪽은 어느 각도로 돌든 반지름 d 인 공 안에 남으므로,
`어깨x − 위로뻗은길이 < 몸통반지름` 이면 이음매가 어떤 각도에서도 안 벌어진다.
`characterGeometry.test.ts` 가 이 부등식을 지킨다.

## 패널은 화면을 통째로 쓴다

경력 · 사진첩 · 방명록은 가운데 뜨는 창(max-w-2xl)이었다. 그래서 어느 화면에서도
컨텐츠가 좁은 관에 담겼다 — 27인치에서는 양옆이 텅 비고, 폰에서는 창 테두리가 화면 폭을
먹었다. 이 앱에서 패널을 여는 건 "잠깐 들여다보는" 게 아니라 **읽으러 들어가는** 행동이라,
그 시간 동안 뒤의 3D 는 볼 일이 없다.

⚠ 전체화면이라고 **글줄까지 늘이지 않는다.** 껍데기(`components/island/Panel.tsx`)는
화면을 다 쓰고, 폭은 컨텐츠가 정한다 — 노트북은 `fill` 로 높이를 다 쓰고, 사진첩은 한 장이 편하게
보이는 34rem, 방명록만 화면 끝까지(쪽지가 많이 보이는 게 게시판의 인상이라서).
제목 줄도 같은 폭을 받는다(`titleClassName`) — 안 맞추면 제목만 안쪽으로 들어가 어긋난다.

닫기는 X 가 아니라 **"← 섬으로"** 다. 전체화면에서는 창을 닫는 게 아니라 돌아가는 것이다.

### 노트북은 원본을 띄운다

경력을 `content/profile.json` 에 베껴 적어 타임라인으로 그렸던 적이 있다. 그런데
제대로 만들어 둔 포트폴리오가 이미 따로 있는 마당에 같은 내용을 두 곳에 두면
**반드시 어긋난다** — 한쪽만 고치는 날이 오고, 그날부터 어느 쪽이 맞는지 알 수 없다.
별 수나 가입자 수처럼 계속 변하는 숫자는 특히 그렇다.

지금은 책상 노트북이 `owner.site` 를 iframe 으로 띄우기만 한다. 원본이 바뀌면 섬도 바뀐다.
껍데기는 **브라우저 창** 모양이다 — 걸어가서 연 건 책상 위 노트북이고, 그 노트북이
웹사이트를 띄웠다면 화면에는 브라우저가 있어야 한다. 주소창과 신호등 점 셋이
"지금 남의 사이트를 보고 있다"를 말해준다.

⚠ iframe 이 `X-Frame-Options` 로 막혔는지는 **JS 로 알 수 없다.** 막힌 프레임도 `load` 가
뜨기도 하고 안 뜨기도 해서 어느 쪽도 신호로 못 쓴다. 그래서 9초를 세고 안 열리면
"새 탭에서 열기"를 내놓는다 — 시간으로 재는 게 정직한 유일한 방법이다.
(GitHub Pages 는 그 헤더를 안 보내므로 지금 주소로는 잘 뜬다. 주소를 옮기면 달라질 수 있다.)

### 사진첩은 피드다

폴라로이드 격자였다. 예뻤지만 한 장이 엄지손톱만 해서 사진을 **보는** 게 아니라
사진이 있다는 걸 확인하는 화면이었다. 지금은 세로로 흐르는 한 줄 — 위에 누가 올렸는지,
가운데 4:5 사진, 아래 이름 굵게 + 설명. 모두가 이미 손에 익힌 형식이라 배울 게 없다.

⚠ 좋아요 수는 **없다.** 피드 모양은 빌리되 없는 숫자를 지어내지 않는다.
아무도 안 누른 하트에 128 이 적혀 있으면 그 순간 이 화면 전체가 못 믿을 것이 된다.

## 화면이 좁으면 카메라가 물러난다

three 의 `fov` 는 **세로** 화각이라, 화면이 세로로 길어져도 세로 범위는 그대로고
**가로만 좁아진다**(가로 폭 = 2 · 거리 · tan(fov/2) · 종횡비). 16:9 에서 편하던 화면이
세로 폰(0.46)에서는 가로가 4분의 1로 줄어 좌우가 캐릭터로 꽉 찬다.

`game/camera/framing.ts` 가 종횡비 하나로 거리 배수를 낸다. **터치 여부가 아니라
종횡비**를 보는 이유는, "모바일이면 멀리" 로 잡으면 가로로 돌린 폰(2.16 — 데스크톱보다 넓다)
까지 쓸데없이 물러나기 때문이다. 문제는 기기가 아니라 화면 모양이다.

배수는 `√(1.6 / 종횡비)` 를 1~1.5 로 자른 값이다. 가로 폭을 그대로 유지하려면 거리를
종횡비에 **반비례**시켜야 하는데(24m → 93m) 그러면 캐릭터가 점이 된다.
제곱근은 좁아진 만큼의 절반쯤만 물러나는 타협이고, 상한 1.5 는 그 타협의 끝이다.

### 아래 가장자리는 조작이 다 쓴다

폰에서 조이스틱(왼쪽 아래)과 점프·밀기(오른쪽 아래)가 화면 아래를 차지한다.
데스크톱 배치(가운데 아래 한 줄)를 그대로 두면 채팅 독이 그 위에 정확히 겹쳐 앉는다 —
**데스크톱에서는 조이스틱이 없으니 개발 중엔 영영 안 보이는 종류의 버그다.**

그래서 손가락 화면에서는 감정표현이 오른쪽 세로줄로 서서 액션 버튼 위에 쌓이고,
말 걸기는 조이스틱과 액션 버튼 **사이 빈 자리**에 동그란 버튼 하나로 앉는다.
상호작용 프롬프트도 더 높이 뜨고, `?` 단축키 버튼은 아예 안 나온다 —
자리가 겹치기도 하지만 키보드 없는 기기에 WASD 표를 띄울 이유가 없다.

조작 UI 가 서로 자리를 비켜주려면 **누가 화면 어디를 쓰는지**를 한 곳에서 알아야 한다.
`game/hud/touch.ts` 의 터치 여부와 `useHudStore.chatOpen` 두 값이 그 역할이다 —
입력창이 열리면 조이스틱이 스스로 사라진다(소프트 키보드가 그 자리를 가져가니까).

## 파티클 물리

궤적은 CPU 가 아니라 셰이더가 푼다 — 링버퍼에 초기 조건만 써넣고 그 뒤엔 아무것도 안 한다.
저항이 걸린 등가속 운동의 해석해를 쓰므로 60fps 든 30fps 든 폭죽이 같은 높이까지 올라간다.

⚠ 이 공식은 **GLSL 과 TS 에 두 벌** 있다(셰이더용 · 폭발 지점 계산용). 공유할 방법이 없어서
`reactionBursts.test.ts` 가 자유낙하로 검산한다 — 한때 부호를 뒤집어 적어서
저항이 약할 때 중력 항이 통째로 상쇄됐고, **색종이가 떨어지는 대신 떠올랐다.**
눈으로는 "좀 이상하다" 정도로만 보였다.

## UI 는 세계와 같은 재료로 만든다

`components/island/ui.ts` 한 곳에 나무·종이·산호색과 "눌리는 버튼" 규칙이 있다.
화면은 게임인데 UI 만 어두운 유리판에 얇은 테두리, 작은 모노스페이스였던 시절이 있었다 —
개발자 사이트의 문법이라 3D 섬 위에 얹히니 "게임 위에 웹페이지를 띄운" 꼴이었다.

지키는 규칙 셋:

- **두꺼운 아랫단** — 버튼 아래 짙은 테두리 4px, 누르면 그만큼 내려앉는다
- **짙은 외곽선** — 밝은 하늘·잔디 위에서도 형태가 안 끊긴다 (반투명은 배경이 밝으면 사라진다)
- **꽉 찬 색** — 블러 대신 불투명. 화면 위에 **놓인 물건**이라 뒤가 비치지 않는다

말풍선처럼 몸통 + 꼬리로 된 모양은 조각마다 테두리를 주면 맞닿는 자리에 선이 남는다.
`OUTLINE` 은 drop-shadow 를 사방으로 겹쳐 **합쳐진 실루엣의 바깥**만 칠하므로 이음매가 없다.

방명록 패널이 코르크판에 포스트잇인 이유도 같다. 걸어가서 연 화면이 3D 게시판과
다른 물건이면 그 순간 몰입이 끊긴다.

## 이동이 빠른 이유

`game/player/simulation.ts` 의 `DEFAULT_MOVE` 가 튜닝 패널 슬라이더의 **최댓값**이다.
걷기 10m/s · 달리기 3배라 반지름 26m 인 섬을 2초면 가로지른다. 산책이 아니라 질주다.

밀치기 세기(`shared/presence.ts` 의 `SHOVE_IMPULSE`)는 여기 **딸려 움직여야 한다** —
걷기를 3.4 → 10 으로 올렸을 때 밀쳐진 사람이 걷는 것보다 느려져서 기능이 죽었던 적이 있다.
느낌을 되돌리려면 개발 서버의 "이동" 패널에서 슬라이더를 내려보고 마음에 드는 숫자를 적으면 된다.
