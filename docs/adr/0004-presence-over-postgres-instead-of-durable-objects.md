# 0004. 실시간 접속자를 Durable Objects 대신 Postgres 폴링으로 만든다

## 상태

채택 (2026-08)

## 맥락

기획서 §5 는 실시간 레이어를 Cloudflare Durable Objects 로 분리하자고 한다. 근거는 타당하다 —
Vercel Functions 는 WebSocket 커넥션이 개별 인스턴스에 핀되고 인스턴스 간 브로드캐스트 수단이
없어서, 같은 방인데 서로 안 보인다. DO 는 키당 인스턴스가 정확히 하나임을 런타임이 보장하므로
그 문제가 구조적으로 사라진다.

그런데 이 프로젝트의 자원 전제는 **"Postgres + Vercel"** 하나다. DO 를 넣으면:

- 배포 대상이 2개가 되고 로컬 개발에 `wrangler dev` 를 병행해야 한다
- CORS · 인증 경계가 하나 늘어난다
- 아직 만들지도 않은 낙서 캔버스(Yjs)를 위해 그 값을 미리 치르게 된다

지금 필요한 건 "다른 사람이 걸어다니는 게 보인다" 하나뿐이다.

## 결정

**Postgres 를 presence 저장소로 쓰고, HTTP 왕복 한 번으로 송신과 수신을 같이 한다.**

```
POST /api/presence  { playerId, x, z, yaw }
  → presence 테이블 upsert
  → 같은 방에서 최근 12초 안에 살아있던 남들을 돌려줌
```

핵심은 **한 번의 왕복에 두 일을 합친 것**이다. 나눴다면 초당 5회 × 2 = 10회의
서버리스 호출이 됐고, 그건 개인 사이트가 감당할 요금이 아니다.

호출 수를 더 줄이는 장치 셋:

- **dead reckoning** — 5cm 이상 움직였을 때만 200ms 주기, 서 있으면 3초 주기
- **visibilitychange** — 백그라운드 탭은 아예 안 보낸다
- **TTL** — 탭을 그냥 닫아도 12초 뒤 사라진다. "나감" 신호에 의존하지 않는다

그리고 200ms 주기의 뚝뚝 끊기는 좌표는 `game/net/interpolation.ts` 의 스냅샷 버퍼가 메운다.
**320ms 과거를 렌더**하므로 항상 두 스냅샷 사이에 있게 되고, 외삽 없이 보간만으로 부드러워진다.
이 부분은 기획서 §5.3 그대로다 — 전송 수단이 WebSocket 이든 HTTP 든 보간 버퍼는 똑같이 필요하다.

## 결과

- 배포 대상 1개. `pnpm dev` 하나로 전부 돈다
- 새 인프라 0개. Redis 도 WebSocket 서버도 없다
- 지연이 왕복 시간 + 보간 지연(320ms)이다. 격투 게임이라면 실격이지만
  섬을 산책하는 데는 아무 차이가 없다
- **서버리스 호출이 접속자 수에 비례한다.** 걸어다니는 사람 1명당 초당 5회.
  동시 접속이 상시 두 자릿수가 되면 이 방식은 더 이상 싸지 않다 —
  그때가 DO(또는 WebSocket 서버)로 옮길 시점이고, 옮겨도 클라이언트에서
  바뀌는 건 `game/net/presence.ts` 의 전송 부분뿐이다. 보간 버퍼와 렌더링은 그대로 쓴다
- Postgres 에 초당 N번의 쓰기가 생긴다. presence 는 행 하나를 계속 덮어쓰는 테이블이라
  autovacuum 이 도는 dead tuple 이 쌓인다. 접속자가 늘면 지켜봐야 할 지점
- CRDT 는 여전히 안 쓴다. 플레이어 좌표는 휘발성이고 병합할 이유가 없다 (기획서 §5.1)
